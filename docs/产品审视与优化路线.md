# 社易管（SmartSociety）产品审视与优化路线

> **版本：V6.0｜数据治理 × 自动化治理 × 全域感知 × Web/Android/HarmonyOS 三端架构**  
> **审视日期：2026-08-17**  
> **产品定位：社会团体内部纯管理端。**  
> **明确边界：不参与日常活动报名，不具备社交属性，不建设公众社区，不做会员社交。**

---

# 0. V6.0 核心结论

SmartSociety 下一阶段不应继续以“增加业务页面”为主要开发方式，而应从一个已经较完整的管理 App，升级为：

> **以统一组织数据为底座、以事件和规则为驱动、以流程自动化为执行机制、以全域感知为管理入口，并由 Web + Android + HarmonyOS 三端协同工作的社会团体数字治理平台。**

最终形成：

```text
统一身份/组织/权限
        ↓
统一主数据
        ↓
统一业务模型
        ↓
统一事件
        ↓
规则判断
        ↓
流程/任务/审批/SLA
        ↓
风险/预警/数据治理
        ↓
Web + Android + HarmonyOS 处置
        ↓
结果回写
        ↓
审计/指标/趋势/组织画像
```

核心目标不是“自动化越多越好”，而是：

> **人工重复操作越来越少，组织状态越来越透明，管理责任越来越清晰，业务过程越来越可追溯。**

# 三、推荐端云总体架构

> **Cloud Hosting 主要负责 Web 前端托管，不应被当作通用后端服务器。**

推荐架构：

```text
                         SmartSociety
                              │
             ┌────────────────┼────────────────┐
             ↓                ↓                ↓
          Web端            Android         HarmonyOS
             │                │                │
             └────────────────┼────────────────┘
                              ↓
                       统一身份认证
                              ↓
                         API Gateway
                              ↓
                 ┌────────────┴────────────┐
                 ↓                         ↓
           Cloud Functions            可演进后端服务
                 │                         │
                 └────────────┬────────────┘
                              ↓
                         Cloud DB
                         /       \
                        /         \
             Cloud Storage       Cache
```

Web 前端：

```text
Web App → Cloud Hosting → CDN/HTTPS
```

### 架构原则

1. 三端共享统一数据契约。
2. 三端不得分别实现核心业务规则。
3. 普通查询可以采用 Cloud DB 能力，但关键业务操作优先经过云函数/统一业务服务。
4. 高风险操作必须经过服务端权限、状态和业务规则校验。
5. Cloud DB 是数据底座，不是整个业务逻辑层。
6. Cloud Hosting 不作为任意后端程序运行环境使用。
7. 后续规模扩大时，可在 API Gateway 后增加独立后端服务，不破坏客户端契约。

# 六、P0：主数据与数据治理

## 6.1 主数据原则

同一个人员、组织、项目、会议、决议不得在多个业务模块重复维护。

例如：

```text
Person
 ├─ Member
 ├─ Position
 ├─ ProjectRole
 ├─ ApprovalRole
 └─ GovernanceRole
```

## 6.2 数据质量规则

自动发现：

- 缺失
- 重复
- 冲突
- 无效
- 过期
- 孤立
- 状态不一致
- 关联缺失
- 时间逻辑错误

## 6.3 数据质量闭环

```text
发现
 ↓
问题分级
 ↓
生成治理任务
 ↓
指派
 ↓
修复
 ↓
再次校验
 ↓
关闭
```

## 6.4 数据质量评分

健康度不能只是 UI 层简单扣分，应由真实治理指标计算：

- 完整性
- 唯一性
- 一致性
- 有效性
- 时效性
- 可追溯性

所有评分必须可下钻到具体问题。

# 八、P0：规则引擎与自动化治理

规则统一采用：

```text
WHEN 事件
IF 条件
THEN 动作
```

动作可以是：

- 创建任务
- 发起审批
- 修改状态
- 产生风险
- 发送通知
- 设置 SLA
- 升级责任人
- 生成文档
- 自动归档
- 请求人工确认

任何自动动作必须可解释：

> **触发事件 → 命中的规则 → 判断条件 → 执行动作 → 执行结果。**

高风险操作坚持：

> **系统发现、系统建议、系统推动；关键授权由人完成。**

# 十三、P1：变化感知与趋势异常

从静态阈值逐步升级到趋势感知。

例如：

```text
审批平均耗时
4.2 → 4.5 → 4.8 → 6.8天
```

系统识别：

> 审批效率连续下降。

同时支持：

- 环比
- 同期对比
- 连续异常
- 突变
- 趋势反转
- 长时间无变化

第一阶段优先使用确定性统计规则，不急于引入 AI。

# 十四、P0：组织健康度模型升级

组织健康度至少包含：


每项都必须：

> **指标 → 异常 → 对象 → 原因 → 动作。**

> **治理闭环率**

```text

已指派
 ↓
已整改
 ↓
已验证
 ↓
已关闭
```

真正关闭必须完成验证，而不是简单改状态。

# 二十一、P0：API 与业务服务层

示例：

```text
POST /projects/{id}/progress
POST /resolutions/{id}/execute
POST /approvals/{id}/approve
POST /risks/{id}/resolve
POST /data-quality/{id}/verify
```

每个业务动作统一执行：

```text
认证
 ↓
组织上下文
 ↓
权限
 ↓
状态机
 ↓
业务规则
 ↓
事务写入
 ↓
Event
 ↓
AuditLog
```

这样 Web、Android、HarmonyOS 不会出现三套业务逻辑。

# 三十二、最终产品原则

### 1. 数据先于页面

没有可靠数据，不继续堆 UI。

### 2. 业务先于客户端

核心规则只能有一套，三端只是不同入口。

### 3. 事件先于人工操作

业务发生后系统应该知道发生了什么。

### 4. 感知必须连接行动

预警最终必须进入工作项、审批或整改。

### 5. 自动化必须可解释

每个自动动作都有事件、规则、结果和审计。

### 6. 高风险决策必须保留人工授权

系统可以发现、建议、推动，但关键授权由人完成。

### 7. Cloud DB 是数据底座，不是全部后端

业务逻辑通过统一服务层治理。

### 8. Cloud Hosting 是 Web 托管能力，不替代后端服务

Web 前端与后端业务服务职责明确分离。

### 9. 移动端做执行，Web 做治理配置

避免三个客户端功能失控和重复建设。

### 10. 不追求功能数量，追求治理闭环

最终衡量：

> **人工管理动作减少多少、问题提前发现多少、流程缩短多少、治理闭环多少。**

# 三十三、最终产品形态

SmartSociety 最终不是：

> “社会团体管理 App”。

而是：

> **“社会团体数字治理与多端协同管理平台”。**

最终形成：

```text
                  管理决策
                     ↑
              组织态势/画像
                     ↑
            风险/预警/变化感知
                     ↑
          事件 → 规则 → 自动流程
                     ↑
          统一业务 API / 云端服务
                     ↑
          主数据 / 业务数据 / 审计
                     ↑
                   Cloud DB
                     ↑
        Web / Android / HarmonyOS
```

最终闭环：

> **数据统一治理 → 多端业务发生 → 云端统一校验 → 事件产生 → 规则判断 → 自动推动流程 → 风险/预警 → 人工处置 → 结果回写 → 审计沉淀 → 组织态势更新。**

这套架构既保留鸿蒙云开发 Cloud DB、Cloud Functions、Cloud Storage、API Gateway 的 Serverless 优势，又避免把 Cloud DB 当作客户端直接 CRUD 的“共享数据库”，并为未来接入独立后端服务留下演进空间。

**SmartSociety 的产品边界始终保持：纯管理、重治理、强数据、强流程、全域感知、多端协同；不向社交、公众报名和 C 端活动平台扩张。**
