# 社易管（SmartSociety）手机端产品审视与优化路线

> **版本：V5.0｜数据治理 × 流程自动化 × 全域感知增强版**  
> **审视日期：2026-08-17**  
> **产品定位：社会团体内部纯管理端，不参与日常活动报名，不承担社交/社区属性。**

---

# 0. 本版核心升级

本版在 V4.1“纯管理端、社会团体治理”定位基础上，进一步把产品能力从：

> **“把业务模块搬到手机上”**

升级为：

> **“以数据为底座、以规则为引擎、以流程为主线、以全域感知为入口的社会团体数字治理平台”。**

本版重点不是继续增加大量孤立页面，而是解决管理端更深层的四个问题：

1. **数据是否真实、完整、唯一、可追溯？**
2. **业务发生后，系统能否自动推动下一步？**
3. **异常发生前，系统能否提前感知？**
4. **管理人员打开手机后，能否快速知道组织“发生了什么、哪里有风险、下一步做什么”？**

因此后续产品建设必须形成：

```text
数据采集
   ↓
数据治理
   ↓
业务事件
   ↓
规则判断
   ↓
自动流程
   ↓
任务/审批/提醒
   ↓
执行结果
   ↓
状态回写
   ↓
指标/风险/趋势
   ↓
管理决策
```

这应成为 SmartSociety 后续最大的产品升级方向。

# 二、产品最终定位模型

SmartSociety 应形成四层产品结构：

```text
┌─────────────────────────────┐
│          管理驾驶舱          │
│ 状态 / 风险 / 预警 / 待办 / 趋势 │
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────┐
│          流程自动化层        │
│ 审批 / 任务 / 提醒 / 规则 / SLA │
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────┐
│           业务域层           │
│ 组织 / 会员 / 治理 / 项目 / 财务 │
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────┐
│           数据治理层         │
│ 主数据 / 标准 / 质量 / 血缘 / 审计 │
└─────────────────────────────┘
```

这四层必须统一设计，不能继续按模块分别建设。

# 三、P0：数据治理体系——从“业务数据”升级为“组织主数据”

这是本版最重要的新增方向。

## 3.1 建立主数据体系

核心主数据至少包括：

- 组织
- 人员
- 会员
- 治理机构
- 职务
- 任期
- 项目
- 任务
- 会议
- 议案
- 决议
- 财务科目
- 预算
- 合同
- 文件
- 证照
- 合规事项

所有业务不得各自维护同一份基础数据。

例如：

> “张三”必须来自统一人员主数据，而不是会员、财务、会议、项目各保存一份张三。

## 3.2 统一人员主档

建立：

```text
Person
 ├── 基础身份
 ├── 联系方式
 ├── 会员关系
 ├── 任职关系
 ├── 治理关系
 ├── 项目关系
 ├── 审批关系
 └── 历史关系
```

这样可以支持：

> 人员 → 会员 → 理事 → 会长 → 项目负责人 → 审批人

完整追踪。

## 3.3 组织主档

组织资料必须成为所有业务的根节点：

```text
Organization
 ├── Members
 ├── Governance
 ├── Projects
 ├── Meetings
 ├── Finance
 ├── Documents
 ├── Licenses
 └── Compliance
```

## 3.4 主数据编码

建议逐步建立统一编码：

- 组织编码
- 会员编码
- 项目编码
- 会议编码
- 议案编码
- 决议编码
- 财务单据编码
- 文档编码
- 合同编码

编码必须稳定，不因名称修改而改变。

# 四、P0：数据质量治理中心

系统不仅要“存数据”，还要主动发现坏数据。

## 4.1 数据质量规则

自动检查：

- 必填缺失
- 重复人员
- 重复会员
- 无效联系方式
- 日期逻辑错误
- 任期重叠
- 治理职位空缺
- 会员状态与任职状态冲突
- 项目负责人不存在
- 项目已结束但任务未完成
- 财务记录缺少业务关联
- 预算与实际支出异常
- 文件缺少分类
- 证照已过期

## 4.2 数据质量评分

组织首页增加：

> **数据治理健康度 92%**

分解：

```text
会员档案       96%
组织资料       100%
治理数据       94%
项目数据       91%
财务关联       89%
文档档案       90%
```

点击进入问题清单。

## 4.3 数据问题自动生成任务

例如：

> 发现 8 名会员缺少有效联系方式

系统自动生成：

> 数据治理任务 → 指定秘书处 → 截止日期 → 自动追踪 → 完成后重新校验

而不是只显示一个红点。

> **业务关系图**

# 六、P0：事件驱动的流程自动化

后续系统不应要求用户手动推动所有流程。

建立统一业务事件模型：

```text
Entity + Event + Condition + Action
```

例如：

> 项目创建 + 金额 > 100000 → 自动进入高级审批。

> 证照剩余 90 天 → 自动生成合规任务。

> 任期剩余 180 天 → 自动进入换届准备提醒。

> 任务逾期 3 天 → 通知负责人。

> 逾期 7 天 → 通知上级。

> 逾期 14 天 → 进入风险中心。

## 6.1 事件中心

统一记录：

- 创建
- 提交
- 审批
- 驳回
- 通过
- 变更
- 完成
- 逾期
- 撤回
- 归档
- 删除
- 状态变化

所有重要业务对象都应产生标准事件。

# 七、P0：规则引擎

建立轻量级规则引擎，而不是把大量业务规则硬编码在 Flutter 页面中。

## 7.1 规则结构

```text
当：发生某事件
如果：满足某条件
则：执行某动作
```

例如：

```text
当：报销提交
如果：金额 > 5000
则：增加财务负责人审批
```

```text
当：项目进度更新
如果：完成率低于计划 20%
则：生成项目风险
```

```text
当：会员退出
则：检查其治理任职
若：存在任职
则：生成任职变更任务
```

## 7.2 规则必须可解释

任何自动动作都应显示：

> 为什么产生？依据什么规则？由哪个系统事件触发？

避免管理人员面对“系统自己做了某事”却无法解释。

# 十一、P0：组织态势总览

工作台顶部不应只显示统计数字，而应形成：

> **当前组织状态 + 风险 + 趋势 + 行动建议。**

例如：

```text
组织运行：正常

待处理      12
风险         3
预警         7
数据问题     5
流程阻塞     2
```

然后告诉用户：

> 当前最值得关注：
> 1. 项目 A 已落后计划 18%
> 2. 两项审批超过 SLA
> 3. 三项治理资料即将到期

而不是让用户自己从十几个模块寻找问题。

---

# 十二、P0：风险、预警、事件三级体系

必须区分三个概念。

## 12.1 事件

> 发生了什么？

例如：

- 项目延期
- 付款完成
- 会员退出

## 12.2 预警

> 可能发生问题。

例如：

- 项目预计延期
- 预算即将用尽
- 任期即将到期

## 12.3 风险

> 已经需要管理层介入。

例如：

- 项目严重延期
- 预算超支
- 重大审批长期阻塞
- 关键治理职位空缺

UI 不得把三者全部做成同样的红点通知。

---

# 十三、P0：异常检测与趋势感知

初期不需要复杂 AI，先用确定性规则实现 80% 价值。

## 13.1 时间异常

- 长时间未更新
- 长时间未审批
- 长时间未完成

## 13.2 数值异常

- 支出突然增加
- 预算执行异常
- 项目成本异常

## 13.3 状态异常

- 已完成项目仍有未完成任务
- 已退出会员仍承担当前职务
- 已注销组织仍有运行事项

## 13.4 关系异常

- 审批人同时是申请人
- 项目负责人已失效
- 财务记录无项目归属
- 决议没有执行任务

# 十四、P0：SLA 与流程健康度

所有关键流程都应可衡量。

指标：

- 平均审批时长
- 最大审批时长
- 超时率
- 驳回率
- 重复提交率
- 卡点节点
- 人员负载

工作台显示：

> **流程健康度 87%**

并指出：

> 财务审批平均耗时较上月增加 32%。

这样系统从“流程工具”升级为“流程治理工具”。

# 十五、P0：自动任务中心

系统生成的任务必须与人工创建任务统一管理。

- 来源类型

- 完成条件

> 完成条件：缺失字段全部补齐并通过校验

# 十六、P0：自动提醒必须“有节制”

全域感知不能演变成消息轰炸。

采用：

> **事件聚合 + 优先级 + 去重 + 升级。**

例如 20 个会员档案缺失：

不要发送 20 条通知。

应该聚合成：

> “发现 20 项会员档案数据问题”

只有达到管理阈值才升级：

```text
提醒 → 预警 → 风险 → 管理层通知
```

# 四十四、最终产品原则

今后的所有新增功能必须遵守六条原则：

### 1. 数据先于页面

没有可靠数据基础，就不要继续堆 UI。

### 2. 事件先于人工操作

业务发生后，系统应该知道发生了什么。

### 3. 规则推动流程

能自动推动的，不要求管理人员重复点击。

### 4. 感知必须连接行动

所有预警最终都要能够进入任务、审批或整改。

### 5. 管理数据必须可追溯

任何重要结论都能追溯到原始业务记录。

### 6. 自动化必须可解释、可审计、可控制

系统可以自动发现和推动，但高风险决策必须保留人工授权。

# 四十五、最终产品形态

SmartSociety 最终不应只是：

> **“社会团体管理 App”。**

而应成为：

> **“社会团体数字治理与移动管理平台”。**

最终能力模型：

```text
                 ┌──────────────┐
                 │   管理决策层   │
                 │ 态势/风险/趋势 │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │   全域感知层   │
                 │ 事件/预警/风险 │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │   自动治理层   │
                 │ 规则/流程/SLA │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │    业务层     │
                 │组织/治理/项目/财务│
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │    数据层     │
                 │主数据/质量/血缘│
                 └──────────────┘
```

最终形成真正的管理闭环：

> **数据被统一治理 → 业务事件被自动感知 → 规则自动判断 → 流程自动推动 → 异常自动预警 → 管理人员移动处理 → 结果自动回写 → 数据再次沉淀 → 组织状态持续可感知。**

这才是 SmartSociety 下一阶段最值得建设的核心能力。

**产品方向保持严格边界：纯管理、重治理、强数据、强流程、全域感知；不向社交、公众报名和 C 端活动平台扩张。**
